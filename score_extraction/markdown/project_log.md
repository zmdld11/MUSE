## 2026-07-05 — VER1.0 全链路打通 + 设计 VER2.0

**完成：** 基于 basic-pitch 的初版管道，输入音频 → demucs 分离 → crepe/basic-pitch 音高 → MusicXML。

**核心问题：** basic-pitch 当黑盒用，只拿 note_events，逐帧闪烁噪声、谐波误检、onset 偏移全没处理。输出乐谱单声道、音符重叠 0%、MuseScore 打不开。

**决策：** 读论文（NoteEM, AMT Overview, Self-Attention AMT），设计五层管线架构：acoustic frontend → 转录模型 → 帧级后处理 → 音符级后处理 → 乐谱组装。

## 2026-07-06 — VER2.0 架构重构

**完成：**
- 新建 5 个模块：`transcriber.py`, `frame_post.py`, `note_post.py`, `voice_assign.py`, `pipeline.py` (重写)
- 删除 `pitch_detect.py`（basic-pitch 黑盒 → 白盒 raw onset/frame probs）
- `frame_post.py` 加 HMM 前向-后向平滑 + 自适应阈值 + 连通域标注
- `note_post.py` 加 onset 精修 + 谐波过滤 + 合并去重
- `voice_assign.py` 加钢琴左右手声部分配
- `score_assemble.py` 精简为纯 music21 组装

**踩坑：**
- `part.insert()` + `makeMeasures()` 反复炸，产生 inexpressible durations
- `part.append()` + `n.offset` 也炸，跨小节切分时值错乱
- 最终方案：管线产出干净 MIDI → MuseScore CLI 转 MusicXML

**新发现的问题：** polyphony 从 0% 修到 89%，但音符全叠一起还缺了很多。逐帧 onset verification 形同虚设（min_onset_prob=0.1）。

### 评测修正 (发现 + A/B 验证)

**发现评测 bug — pitch 单位错误：** mir_eval.transcription 的 pitch 参数是 **Hz**，误传了 MIDI 音高号。MIDI 60 vs 61 当 Hz 只差 ~28 cents < 50 cents 容差 → 半音错误被误判为匹配，note_f1 被高估约一倍。

**修复**：`eval/metrics.py` 加 `_midi_to_hz`，调用前统一转 Hz。记入 memory。

**后处理 A/B（修正评测后严格验证）**：

| 配置 | note_f1 |
|------|---------|
| min_frames=4 + 自适应pct50（旧） | 0.271 |
| **min_frames=2 + 自适应pct50（采纳）** | **0.317** |
| min_frames=2 + 固定0.3（曾误改，已回退） | 0.201 |

- `min_frames 4→2` 有效：recall 0.182→0.232
- 阈值改固定 0.3 **有害**：precision 0.500→0.307，recall 反降，是误判
- 更改已回退，只保留 `min_frames=2`

**新增复调分析工具**：`eval/polyphony.py`，按 GT 帧的同步活跃音高数分组统计 recall。

**当前真实基线**（`report_20260731-194519.json`）：

- 模型**能测和弦**：poly≤3 时 recall 与单音持平，复调上限约 poly=4
- 94% 的 GT 音符在和弦里，整体 recall 仍受限于检测灵敏度

## 2026-08-01 — 诊断复核（人工验证，修正 07-31 部分结论）

**背景：** 07-31 日志的诊断由 AI 生成、未经验证。本次对评测链路做了逐音符追踪 + A/B 实测复核（ours 模型，评测集 8 首）。结论与 07-31 有重要出入，以本次实测为准。

**验证方法：** ① 逐音符追踪 GT 音符在「模型输出 → HMM 平滑 → 二值化 → 连通域 → onset 验证 → note_post」各阶段的存活；② 阈值策略与调性过滤的 A/B；③ 分阶段计时定位环境问题。

**实测结论：**

1. **模型不是瓶颈。** 93-95% 的 GT 音符帧概率 ≥0.3（多数 0.999）。07-31"检测灵敏度不足/漏检是模型问题"的归因错误——是后处理把模型已经看到的音符扔了。
2. **真凶一：自适应阈值 ≈ 1.0。** 实测各音区 50 分位阈值 low=1.0 / mid=0.999 / high=0.974（Lange 曲），HMM 后验 0.96-0.99 的真音符被直接灭掉。同样条件下 GT 二值化命中 56/95 → 固定 0.5 阈值时 87/95（Scarlatti 曲 293/361 → 355/361）。
3. **真凶二：note_post 的 top-7 音级"调性过滤"。** 按出现时长取 7 个音级当"调性"、其余全删，对转调/半音丰富的曲子（如 Scarlatti 奏鸣曲）大面积误杀。8 首均值：**关掉它，note F1 0.227 → 0.632（其余配置不动），precision 0.405 → 0.975 不降反升**。
4. **onset 验证 min_onset_prob 不是瓶颈。** 0.2/0.3/0.4/0.5 四档 A/B，3 首 note F1 几乎不变（0.42-0.43）——它砍掉的多是假阳性。07-31 待办里"调 min_onset_prob"划掉。
5. **git 矛盾记录复核。** 曾有提交发现阈值≈1.0 问题并改固定 0.3（声称 F1 0.42→0.64），随后一提交又回退（声称 precision 崩）。两边都带着调性过滤在测，因果混淆；且都没试过固定 0.5。本次实测固定 0.5 显著优于自适应（3 首子集），固定 0.3 未复测，建议全量 A/B 一并测。

**8 首 A/B（note F1 逐首均值）：**

| 配置 | P | R | F1 |
|------|------|------|------|
| 当前（adaptive + 调性过滤） | 0.405 | 0.161 | 0.227 |
| adaptive + 关调性过滤 | 0.975 | 0.475 | 0.632 |
| fixed 0.5 + 调性过滤 | 0.417 | 0.177 | 0.242 |
| fixed 0.5 + 关调性过滤 | 0.981 | 0.416 | 0.567 |

> 注：3 首子集上 fixed 0.5 优于 adaptive，8 首上相反——阈值策略需全量 40 首定案；调性过滤的移除是确定性的大收益。

**环境修复（重要）：** 评测在当前机器上无法直接运行——librosa.stft 首次调用会触发 numba 编译缓存写系统临时目录，此处无限挂起。修复：`$env:NUMBA_CACHE_DIR` 与 `$env:TMP` 指向项目内可写目录（已验证）。另：eval/diagnose.py 第 3 层有 bug（零时长 est 音符使 mir_eval 崩溃），不影响主评测，但需修。

**下一步：** 采用方案 A（最小改动）：二值化阈值策略 + 调性过滤处置，全量 40 首 A/B 定案，再决定是否深入（方案 B 重构）。

## 2026-08-01 — 方案 A 全量 A/B 结果（40 首, seed=42）

**重要修正：** 上文"8 首子集"结论（调性过滤是最大凶手、fixed 0.5 更优）**在全量 40 首上被推翻**——8 首子集里转调/半音曲目（Scarlatti、Satie 等）占比过高，产生选择偏差。以本次全量为准。

**基线之谜（已查清）：** 日志/version_plan 里的基线 note_f1=0.217 是**旧代码状态**的数字——7/31 19:09 提交曾把默认阈值改为 fixed 0.3，19:47 的报告就是用 fixed 0.3 生成的，但被标注为"自适应pct50"；8/1 12:12 提交回退为自适应。**当前代码默认（adaptive + 调性过滤）实测基线 = 0.294**，并非 0.217。

**全量 40 首 A/B（eval.py 统一链路，同条件可比）：**

| 变体 | note_f1 | P | R | offset_f1 | frame_f1 |
|------|---------|------|------|-----------|---------|
| **adaptive + 调性过滤（当前默认）** | **0.294** | 0.504 | 0.211 | 0.112 | 0.983 |
| adaptive + 关调性过滤 | 0.240 | 0.399 | 0.174 | 0.100 | 0.983 |
| fixed 0.5 + 调性过滤 | 0.258 | 0.435 | 0.193 | 0.196 | 0.995 |
| fixed 0.5 + 关调性过滤 | 0.230 | 0.387 | 0.171 | 0.164 | 0.995 |
| fixed 0.3 + 调性过滤 | 0.231 | 0.403 | 0.173 | 0.169 | 0.995 |
| fixed 0.3 + 关调性过滤 | 0.207 | 0.354 | 0.154 | 0.153 | 0.995 |
| adaptive cap0.8 + 调性过滤 | 0.222 | 0.367 | 0.166 | 0.161 | 0.994 |
| fixed 0.7 + 调性过滤 | 0.266 | 0.447 | 0.199 | 0.200 | 0.994 |

**结论：**

1. **简单开关全部打不过当前默认。** 调性过滤全量上是净收益（关掉它 40 首里伤 24 首，虽有个别曲目大赚：Scott Hilarity Rag +0.474 / 大亏：Satie -0.341）；固定阈值虽提高 frame/offset，但音符级引入噪声，precision 从 0.504 掉到 0.35-0.45。
2. **机制结论仍成立，但需要更好的实现：** 自适应阈值≈1.0 杀真音符是真的（HMM 后验 0.96-0.99 被灭、GT 二值化 56/95→87/95）；调性过滤误杀转调曲目也是真的。只是"固定阈值/关闭过滤"这种粗糙手段无法利用这两个发现——下一步应做方案 B（每音高 Otsu/双峰阈值、连通域分音高、K-S 调号+临时记号）。
3. **副产品（对时值目标有用）：** fixed 0.5-0.7 把 offset_f1 从 0.112 提到 0.196-0.200（近一倍），frame_f1 也更高（0.995 vs 0.983）。等音高 recall 达标后调 offset 时，阈值策略值得重测。
4. **模型仍是次要矛盾：** 全量 est/gt ≈ 3510/7529（47%），但命中率只有 ~21%——后处理既漏检又制造未命中噪声，模型侧的优化可以继续往后放。

**代码变更（保留，默认行为不变）：** `frame_post.py`/`note_post.py`/`metrics.py`/`eval.py` 新增 A/B 参数（`--threshold`/`--threshold-cap`/`--key-filter`），默认值均保持原行为；`eval.py` 启动自动修复 numba 缓存挂起；`diagnose.py` 修零时长音符崩溃。

## 2026-08-02 — 错误归因分析（eval/error_analysis.py）

**问题**：note_f1 低（0.294）到底因为什么？漏检 / 多检 / 错检？

**方法**：GT ↔ 预测按 onset±50ms + 音高±50cents 做标准最大匹配（scipy Hungarian，mir_eval 同款），四分类：
- 命中 TP：onset 对 + 音高对
- 错检：onset 对 + 音高错（模型听到了音但音高分错）
- 漏检：GT 处无任何预测（没听到/被后处理删）
- 多检 FP：预测处无 GT（噪声/泛音/幻听）

**全量 40 首结果（ours 模型）**：

| 类别 | 数量 | 占比(GT侧) |
|------|------|-----------|
| 命中 TP | 1356 | 18.0% |
| 错检（音高错） | 788 | 10.5% |
| **漏检** | **5385** | **71.5%** |
| 多检 FP | 2106 | — |

**结论：漏检是绝对主瓶颈（71.5%），错检仅 10.5%。** 音高识别本身不是问题——模型要么听到音且音高对（18%），要么根本没检出（71.5%）。"听到音但音高分错"只占 10.5%。

**按复调度**：单音命中率最高（23.2%），和弦略低但差异不大（14-21%），漏检率所有复调度都在 67-77%——**漏检是均匀分布的，不是和弦特有**。

**按音区**：低/中/高音区漏检率 69-74% 均匀——**不是某个音区的问题**。

**关键推论**：
1. 后处理（阈值/HMM/连通域/调性过滤）把模型已检测到的音符杀掉了——之前 diagnose 验证过 95% GT 音符帧概率≥0.3，但最终只剩 18% 存活
2. "多检 2106 ≈ est 总数 3440 - 命中 1356"——多检也不算多，问题是**检出的太少**
3. 错检 10.5% 指向音高头或 CC 合并（相邻半音），是第二战场

**下一步**：既然漏检 71.5% 且模型层检测良好（95% 激活），后处理各环节（二值化→连通域→长度过滤→onset验证→谐波→调性）中哪一步杀最多？需要逐层存活追踪（diagnose.py 已有雏形，待补全到 note_post 全链）。

### 1. convert_himawari.py 审查结论（对照 C++ 原版 play_single）

**解析逻辑与 C++ 完全一致**（逐字符验证）：

**d) 碎音根源: 模型过度检测（不是混音串扰！）**

- 怀疑: pipeline 对 piano 轨用原音频（含鼓/贝斯/人声）转写 → 串扰碎音
- 验证: 转写分离后的钢琴轨（demucs 单独 piano）→ 1521 音符, precision 37.1% vs 原音频 36.6% **无改善**
- **结论: 碎音 = 模型/BP 后处理把真实钢琴的泛音、踏板共鸣、弱音检测成音符**（官方 BP 也有 54% 碎音，但比我们少 9 点）
- 之前"一个 GT 音符被切成 ~5 个碎音"的画像成立：帧概率抖动 + 后处理参数（min_note_len=5/energy_tol=5 按 hop 缩放）在真实录音上偏松

**下一步方向（排序）**:
1. 真实录音用官方 BP 推理+后处理（recall 91% vs 61% 差距太大，先确认是否值得换推理路径）
2. 碎音合并: 同音高相邻碎音 merge/gap-fill → recall/precision 双升
3. 用户提议的 onset 抢占算法（新音开始 → 断掉不可能存在的旧音）做 offset
4. 真实录音对比脚本固化: --gt e + 偏移校正默认开启

### 5. 权重/后处理归因实验（隔离 29 点差距的构成）

**先排除移植差异**: 0.5/0.3 阈值下我们的 process_frames_bp = 官方 output_to_notes_polyphonic = **1651 音符完全一致** → 移植零差异！
（此前 3112 vs 1651 的 1.9 倍差 = 阈值 0.4/0.2 vs 0.5/0.3，非移植 bug）

**同阈值矩阵（真实录音, E 大调 GT, 偏移校正）**:

| 阈值 | 权重 | min_note_len | 音符数 | recall | precision | F1 |
|------|------|------|--------|--------|-----------|-----|
| 0.5/0.3 | 官方 | 11 | 1651 | 89.9% | 45.9% | **0.61** |
| 0.5/0.3 | 我们 | 5 (缩放) | 1292 | 61.6% | 40.2% | 0.49 |
| 0.5/0.3 | 我们 | 11 (官方) | 991 | 58.4% | 49.6% | 0.54 |
| 0.4/0.2 | 官方 | 11 | 3112 | 96.0% | 26.0% | 0.41 |
| 0.4/0.2 | 我们 | 5 (缩放) | 1521 | 66.9% | 37.1% | 0.48 |
| 0.4/0.2 | 我们 | 11 (官方) | 1215 | 64.5% | 44.8% | **0.53** |

**归因结论**:
1. 后处理移植: 零差异 ✓（同配置 1651=1651）
2. **权重差距真实存在**: 同配置下官方 recall 高 ~28-30 点（89.9 vs 61.6; 96.0 vs 66.9）→ 官方权重在真实录音上更强, 根源=训练数据分布（MAESTRO 真实 vs GiantMIDI 合成）
3. **参数发现**: 真实录音上官方参数（min_note_len=11 不按 hop 缩放）优于我们的缩放策略（5）→ F1 0.48→0.53；合成评测上 5 更优 → **后处理参数需按域选择（域自适应后处理 = 论文素材）**
4. 我们的最佳 F1 0.53-0.54 vs 官方最佳 0.61 —— 差距收窄到 ~0.08（权重+参数双修正后）

**对论文的意义**: 模型差距是训练数据分布问题（非架构）→ "合成预训练 + 真实微调" 是明确改进路径; 双域评测 + 域自适应后处理可作贡献点。

### 6. 碎音抑制实验: 弱音过滤 + 钢琴轨 + wiener 降噪 (F1 0.46 → 0.63)

**背景**: 用户质疑"碎音是泛音吗"→ 数据分析推翻泛音主导论:
- 主音生命周期内 est 音符分类: 合法声部 1750 / 其他碎音 2596 / 主音泛音 193 (仅 6.4%) / 同音高碎片 115
- **决定性证据**: 碎音音级分布 = GT 音级分布 (都是 E 大调 {1,3,4,6,8,9,11}) → 碎音是"谱面没写的真实演奏内容"(装饰/加花/八度重复/低音细节), 不是模型幻觉
- 碎音 54% 集中在音符尾部, 但主体非泛音 → 泛音假说只解释 6%
- 启示: 无脑碎音过滤会砍真内容 (同 key filter 教训), 应走"弱音过滤 + 声源选择 + 降噪"

**实验 (真实录音, E 大调 GT, 分段偏移校正)**:
| 配置 | 音符数 | recall | precision | F1 |
|------|--------|--------|-----------|-----|
| 原音频 (pipeline 现状) | 1408 | 61.1% | 36.6% | 0.46 |
| 原音频 + conf≥0.5 | 679 | 52.2% | 64.8% | 0.58 |
| 钢琴轨 + conf≥0.5 | 757 | 56.9% | 63.4% | 0.60 |
| **钢琴轨 + wiener降噪 + conf≥0.5** | 844 | 62.9% | 62.8% | **0.63** |
| 钢琴轨 + wiener + conf≥0.4 | 1057 | **70.3%** | 56.1% | 0.62 |

**结论**:
1. **弱音过滤有效** (谱面无弱音技巧 → 弱音=碎音): precision +28 点 (36.6→64.8%), recall 仅掉 8.9 点
2. **demucs 雪花确认存在且可解**: wiener(mysize=9) 降噪后 recall +6 点 (56.9→62.9%) — 用户怀疑正确
3. **钢琴轨 > 原音频**: 串扰影响 > 雪花影响, pipeline 应改用钢琴轨转写 (推翻旧判断)
4. 同音高 merge 无效 (BP 后处理天然合并同音高, 碎音主体是不同音高)
5. 短音过滤无效 (碎音中位数时值 0.70s, 是完整形态的弱音)

**待办**: 听感验证 piano_stabilized.mid; 固化到 pipeline (piano 用钢琴轨 + wiener + conf 过滤); 更稳的降噪 (spectral gating 替代 wiener NaN 问题)

### 7. 膝跳反射回声定位 + VER2.4 管线固化 (F1 0.56→0.65)

**现象**: 用户听感 — 主音响完约 16 分音符后, 一个比主音低、像"中央C左边B"(B3≈59) 的音弹一下

**定位**: 不是同音高回声 (谱面有 33% 快速重复音, 时间-音高模式规则全部误伤, recall 大出血 45%), 而是:
- 低 onset_prob (<0.15) 候选 771 个中 GT 真音符仅 30.7%; onset_prob>0.8 的 88.3% 是真音符 — **无真实击键的弱音 = 回声伪音符** (melodia_trick 捡起的衰减尾巴/共鸣)
- B 音系列碎音偏多 (B1/B2/B3/B4 共 155 个), 用户听到的 B3 是共鸣最响的频率
- 碎音音级分布 = GT 音级分布 (E 大调) → 音乐上有意义, 无脑过滤会砍真内容

**规则**: 删 (onset_prob<0.15 且 confidence<0.5) → 1492→968 音符, recall 78.1→70.1%, precision 44.1→61.1%, **F1 0.56→0.65**

**VER2.4 管线固化** (src/pipeline.py + src/frame_post.py):
1. piano 轨改用钢琴轨 + wiener 降噪 (原音频串扰 + demucs 雪花, F1 0.46→0.63)
2. process_frames_bp 候选增加 onset_prob 字段 (onset 时刻窗口峰值)
3. Layer 4 膝跳回声过滤 (onset_prob<0.15 且 conf<0.5)
4. 修路径 bug: _process_instrument 输出目录改用歌曲目录 (钢琴轨降噪临时文件名会污染派生目录)
- 端到端验证: 真实录音 pipeline 跑通, piano 914 音符, MIDI/XML 输出正确

**工具**: eval/piano_roll.py — 卷帘 PNG + 音符 CSV (人工核对) + CSV 修正后 rebuild 重生成 MIDI

## 2026-08-03(凌晨) — A1 碎音合并实验：后处理救不了真实录音，根因=模型域差

### 背景
真实录音诊断 (08-02晚) 结论是"一个 GT 音符被切成 4.7 个碎音"，按此设计碎音合并 (A1)。

### 实验 (夜の向日葵, E大调 GT, shift=0.15s)

**1. 碎音合并 (merge_similar_notes, TDD 8 测试)** — ❌ 失败
| gap_tol | 音符数 | 50ms-P/R/F1 | 窗口R |
|---|---|---|---|
| 0 (基线) | 1407 | 12.9/21.5/16.1 | 54.4% |
| 2 帧 | 1159 | 12.4/17.1/14.4 | 45.0% |
| 12 帧 | 944 | 13.3/14.9/14.1 | 39.6% |
合并减少音符但 recall 全线下滑 → **误合真实快速音符**。

**2. 真相修正**: "碎音" 假设错误 — 同音高 est 音符仅 0.8 个/GT 音符 (4.7 是**任意音高**，即 GT 窗口内大量**音高错误**的音符)。真实问题 = 音高错误音符 (杂音)，不是同音高碎音。

**3. amplitude 过滤** — ❌ 失败: 真 0.581 vs 杂 0.408 (中位)，区分度不足，F1 16.1→16.3% 封顶。

**4. 杂音音级分析**: 杂音 pitch classes = E 大调音阶 (B 最多 181) — 调内音被错误检测，非泛音。

**5. basic-pitch 官方模型对比** — 重要发现
| 模型 | 音符数 | 50ms-P/R/F1 | 窗口R |
|---|---|---|---|
| ours (自训) | 1407 | 12.9/21.5/16.1 | 54.4% |
| basic (官方) | 3101 | 10.4/38.2/16.3 | **76.7%** |
basic-pitch (MAESTRO 真实录音训练) 真实录音拾音远强 (recall 38% vs 21.5%, 窗口 77% vs 54%)，但杂音更多。

**6. 分离钢琴轨** — ❌ 几乎无效: ours 窗口 54.4→56.6% (+2pp), basic F1 16.3→17.7%。混音串扰非主因。

### 结论
- **后处理层面 (合并/过滤/分离轨) 全部救不了真实录音** — 瓶颈在模型对真实音频的输出质量 (D1 模型域差)
- 自训模型 (FluidSynth 合成训练) vs basic-pitch (真实录音训练) 在真实场景差距显著
- **下一步: D1 真实域 (真实录音微调/数据增强) 是唯一大方向**；或真实录音场景改用 basic-pitch (拾音全但杂音多)
